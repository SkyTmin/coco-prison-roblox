## 0. Главные решения одним списком

1. **Шахта — это формула, а не склад кубов.** Какая руда лежит в любом слое, вычисляется из номера слоя и «зерна» (сида)
   шахты. Хранятся только выбитые места — как список отрезков «здесь пусто от и до» в каждой дорожке.
2. **Руда раскладывается «квотами» по отрезкам из 50 слоёв.** Поэтому подсчёт 75 000 выбитых блоков — это ~1 500 простых
   сложений, а не 75 000 проверок. Пересчёт точный, не «примерно».
3. **Сервер решает всё**: клиент шлёт только «ударил по клетке (x, y, глубина)». Форму удара, молнии, каскады, деньги,
   находки, сдвиг стены считает сервер. Клиент рисует и анимирует то, что сервер уже решил.
4. **Клиент не знает зерна шахты.** Сервер присылает только состав видимого окна (20 слоёв). Так нельзя «просветить»
   шахту читом.
5. **Кубы — только на клиенте и только видимые.** Ни один блок шахты не реплицируется движком: это локальные детали из
   пула (≤ 1 000 штук, обычно 100–400 на экране).
6. **Езда стены — анимация смещения всего окна**, а пройденные пустые слои не рисуются вообще (их и так нет).
7. **Переносим из «Каторги» инфраструктуру** (профили, сохранение, бустеры, аукцион, топы, донат, кейсы с шансами,
   строки на 4 языках, звук, Blender-пайплайн, реле Studio). **Пишем заново** всё, что про шахту, кирки и интерфейс.
8. **Порядок — вертикальный срез сначала**: одна шахта + одна кирка + автопродажа + езда стены + молния, проверка на
   телефоне. Только потом ширина.
9. **Симулятор экономики запускает настоящий код игры** (Luau через Lune), а не копию формул на JavaScript — цифры не
   разъедутся.

## 1. Модель данных бесконечной шахты

**Простыми словами.** Представь стену 5×3 блока, за ней следующая стена, и так бесконечно — это «слои». Каждую клетку
можно назвать тремя числами: колонка `x`, ряд `y`, номер слоя `d` (глубина). «Дорожка» — это все клетки с одинаковыми
`x, y`, уходящие вглубь, как труба. Мы не храним кубы. Мы храним: (1) зерно шахты — число, из которого по формуле
получается, где какая руда; (2) номер переднего слоя; (3) для каждой дорожки — где в ней уже пусто. Пробитая на 5 000
слоёв дыра — это одна запись «в дорожке (2, 1) пусто с 300 по 5 300», а не 5 000 записей.

### 1.1 Координаты и константы [решение]

| Имя | Значение | Смысл |
|---|---|---|
| `x` | от `-R` до `R`, центр = 0 | колонка. Отсчёт от центра: при расширении стены (5 → 7 → 9) добавляются крайние дорожки, старые координаты не меняются |
| `y` | `0 … H-1`, 0 = пол | ряд |
| `d` | `0, 1, 2 …` (целое, до 2^31) | абсолютный номер слоя |
| `S` | 5 стадов | размер блока (настроить на телефоне: стена 5×3 целиком на экране) |
| `C` | 50 слоёв | длина «отрезка» дорожки для квот (делит длину пласта) |
| `STRATUM_LEN` | 100 слоёв | пласт (PLAN п. 15) |
| `WINDOW` | 20 слоёв | сколько слоёв клиент знает и может рисовать; туман с ~14-го |
| `MAX_W × MAX_H` | 15 × 7 | наибольшая стена; `laneKey = (x + 7) * 8 + y` (≤ 120 дорожек) |

### 1.2 Что берём из html-прототипа, что нет

Прототип (`class Mine`) хранит для каждой дорожки одно число — глубину первой целой клетки (`lanes[]`), `front` = минимум
по дорожкам, `nextFront()` = `Math.min(...lanes)`. Это верно и компактно, **но только если дырки всегда начинаются у
фасада**: прототип сам это пишет («exact for front-facing cuts, not arbitrary tunnels»). Наши кирки ломают и в глубине:
молния прыгает внутрь, взрыв сферой, разлом — трещина, которая может начинаться не у фасада, а за целой клеткой.

Берём: идею «дорожка = одно число вершины» (`top`), правило «стена едет на минимум», функцию `pattern(kind)` как
каталог форм, хэш клетки, проверку при загрузке сохранения (`restore` отвергает битые данные), запрет на двойное
начисление за одну клетку (`breakBlock` удаляет клетку один раз).
Не берём: `extract(count)` с перебором по одному (O(N × дорожки)), руду «по хэшу каждой клетки» (тогда подсчёт тысяч
блоков = перебор тысяч хэшей), жёсткие 9×3 в `restore`.

### 1.3 Хранение пустот: «вершина + отрезки»

```lua
-- src/shared/Mine/MineState.luau  (--!strict, --!native)
export type MineState = {
	v: number,            -- версия формата
	seed: number,         -- зерно шахты (u32), только на сервере
	width: number, height: number,
	front: number,        -- первый слой, где есть хоть один целый блок
	top: { [number]: number },     -- laneKey → первая глубина, где МОЖЕТ быть целый блок (всё в [front, top) пусто)
	holes: { [number]: { number } }, -- laneKey → плоский отсортированный список [a1, b1, a2, b2, …]: пусто в [a, b), все a > top
	holeCount: number,    -- сколько отрезков всего (для лимита)
	damage: { [number]: number },  -- клетка → накопленный урон (только для «крепких» блоков; не сохраняется)
}
```

Инварианты (проверяются в тестах и при загрузке):
- `front = min(top[lane])` по всем дорожкам текущей стены;
- в `holes[lane]` отрезки не пересекаются, не соприкасаются, отсортированы, первый `a > top[lane]`;
- нормализация: если первый отрезок начинается ровно в `top`, он «съедается»: `top = b`, отрезок удаляется.

Основные операции:

```lua
isSolid(st, lane, d)       -- d >= top[lane] и d не попал в отрезок (двоичный поиск) → O(log k)
removeRange(st, lane, a, b, out)
	-- вычитает уже пустые куски из [a, b), оставшиеся целые куски добавляет в out (для подсчёта руды),
	-- вставляет [a, b) в список с объединением соседей, нормализует top. O(k) на дорожку.
advance(st) -> delta       -- newFront = min(top); delta = newFront - front; front = newFront
```

**Правило «передний слой не пуст — не едем»** выполняется само: `front` — это минимум вершин; пока хоть одна дорожка
имеет целую клетку на глубине `front`, минимум не сдвинется, как бы глубоко ни были пробиты остальные.
**Проезд пустых слоёв одним движением** — тоже сам: если слои 101–103 пусты во всех дорожках, после нормализации все
`top ≥ 104`, `advance` вернёт `delta = 3` (или 300 — без разницы), клиент анимирует один съезд.
**Расширение стены**: новым дорожкам ставим `top = front` (они целые от фасада). Старые дыры не трогаем.

**Лимит.** `holeCount ≤ 4 000` [решение]. Внутри окна (20 слоёв) отрезков не больше, чем клеток (≤ 2 100 при 15×7) —
этого хватает. Глубже окна (дальше 20 слоёв) способности кирок по правилу **режут только «прогонами»**: целый отрезок
дорожки (разлом, молния вглубь) или целые слои (ульта). Тогда одна способность = 1 отрезок на дорожку. Если всё же лимит
превышен — сервер «дорезает» мелкие глубокие дыры до целых слоёв **в пользу игрока** (награда за дорезанные блоки тоже)
и пишет предупреждение в лог. Дыры никогда не заполняются обратно (PLAN п. 5).

### 1.4 Генерация руды: квоты по отрезкам

**Простыми словами.** Каждая дорожка разбита на куски по 50 слоёв. Для каждого куска формула сначала решает «сколько»
(например: 38 камня, 8 угля, 3 железа, 1 золото), а потом «где» (в каком из 50 мест что лежит). Чтобы узнать, сколько
золота в 100 целых кусках, достаточно сложить 100 «сколько», не раскладывая «где». Раскладывать приходится только два
крайних куска и то, что видно на экране.

```lua
-- src/shared/Mine/MineGen.luau (--!native). Чистые функции, одинаковые на сервере и в симуляторе.
-- h(seed, x, y, c, salt) -> [0, 1): целочисленный хэш (bit32), детерминирован на любой машине.

function MineGen.quota(seed, x, y, c): { [oreIndex]: count }
	local s = Strata.of(c * C)                        -- пласт этого куска
	local w = Strata.weights(s)                       -- доли руды пласта из конфига, Σ = 1
	local rich = 1 + s.richness * (2 * h(seed, x, y, c, 1) - 1)  -- «богатые» и «бедные» куски (жилы)
	local out, used = {}, 0
	for k = #w, 2, -1 do                              -- от самой редкой к обычной; 1 = «пустая порода»
		local e = C * w[k] * (k >= s.rareFrom and rich or 1)
		local n = math.floor(e) + (h(seed, x, y, c, 10 + k) < e % 1 and 1 or 0)  -- случайное округление
		n = math.min(n, C - used); out[k] = n; used += n
	end
	out[1] = C - used                                 -- остаток — порода
	return out
end

function MineGen.cells(seed, x, y, c): { oreIndex }   -- раскладка куска, кэш LRU на ~256 кусков
	local q = MineGen.quota(seed, x, y, c)
	-- места ранжируются по ГЛАДКОМУ шуму n(x, y, d) (value noise с шагом 3 клетки + крошечный хэш на ничьи).
	-- Самые «высокие» места получают самую редкую руду. Шум гладкий по x и y, поэтому редкая руда в соседних
	-- дорожках оказывается на близкой глубине → объёмные жилы и скопления (нужны молнии и «куда бить», PLAN п. 12).
	local order = sortByNoiseDesc(x, y, c * C, C)
	... раздать q[k] мест начиная с редких
end

function MineGen.specials(seed, x, y, c): { {d, kind} }  -- особые блоки и находки куска: 0–2 штуки
	-- число: h < p(stratum); место: floor(h * C); тип: взвешенная таблица пласта (сундук, окаменелость, бомба,
	-- бонус-блок, ключ, кристалл «золотая жила» …). Особый блок заменяет руду в своей клетке.
end

function MineGen.rangeHist(seed, x, y, a, b, hist, finds)  -- сколько какой руды в [a, b) одной дорожки
	for c = a // C, (b - 1) // C do
		local lo, hi = math.max(a, c * C), math.min(b, (c + 1) * C)
		if lo == c * C and hi == (c + 1) * C then addQuota(hist, MineGen.quota(seed, x, y, c))   -- O(число руд)
		else local cells = MineGen.cells(seed, x, y, c); for d = lo, hi - 1 do hist[cells[d - c * C + 1]] += 1 end end
		collectSpecials(MineGen.specials(seed, x, y, c), lo, hi, finds)      -- особые: вычесть из hist, добавить в finds
	end
end
```

Стоимость ульты «5 000 слоёв × 15 дорожек»: 15 × (100 полных кусков + 2 крайних) ≈ 1 500 квот × ~8 руд + 2 × 15
раскладок по 50 клеток ≈ 15 000 простых операций. «25 000 слоёв × 45 дорожек» ≈ 22 500 квот ≈ 200 000 операций —
в нативном Luau это единицы миллисекунд [оценка, замерить в этапе 1]. Для сравнения, перебор «по клетке» на тех же
25 000 × 45 = 1,1 млн клеток с хэшем и выбором руды — в десятки раз дольше.

**Почему квоты, а не хэш каждой клетки:** точный подсчёт за удар быстро и честно (за 75 000 блоков игрок получает ровно за
то, что в них лежало), плюс квоты гарантируют, что «невезучих» длинных пустых кусков не бывает — ребёнок всегда видит
руду. Минус: внутри куска руда не независима (чуть менее «случайно»); ребёнок этого не заметит.

**Пласты.** `Strata.of(d) = d // STRATUM_LEN`; у пласта: набор руды и доли, цена руды, «крепость» (`hitsToBreak` для
слабой кирки — см. 1.6), цвет стен тоннеля, музыка, шанс особых блоков. После последнего описанного пласта — формула
(цены ×k, повтор набора с новым цветом) — шахта бесконечна. Куски длиной 50 не пересекают границу пласта (100 делится
на 50).

**Зерно.** Своё у каждого игрока, новое при перерождении [решение]. Хранится только на сервере.

### 1.5 Награда за логические блоки

`hist` (сколько какой руды) → деньги = Σ `hist[k] × price[k]` × множители (бустеры 2+2+2 = ×6 по BRIEF, Разгон,
Лихорадка, карточки). Статистика, задания, достижения читают тот же `hist`. **Редкие дропы на тысячах блоков** (ключи,
кейсы) — не бросок кубика на каждый блок, а **накопитель**: `p.acc.key += blocks × chance`; пока ≥ 1 — выдать ключ и
вычесть 1. Плавно, без серий невезения, нечего «фармить» перезаходом. Находки (сундуки, окаменелости) — это конкретные
особые клетки из `specials`, их можно взять ровно один раз, потому что клетка удаляется один раз.

**Числа.** Деньги — обычное число Luau (double). Отказываемся от `moneyScale` (тысячные доли) старой игры: в симуляторах
суммы растут до триллионов; double точен до 9·10^15 и годится для показа «1.15T». Формат «1.15K / 1.15M / B / T / Qa»
— `src/shared/Format.luau`. **Ловушка:** OrderedDataStore хранит только целые (int64) → в топ «по деньгам» пишем
`floor(log10(money) × 10^6)` и показываем обратно (позиции сравниваются верно).

### 1.6 Удар и «крепость» блоков

По умолчанию блок фасада ломается одним ударом своей формы (детям понятно). Пласт может иметь «крепость» больше силы
кирки → нужно `ceil(крепость / сила)` ударов; урон копится в `damage[cell]` (только клетки окна; не сохраняется, при
перезаходе обнуляется). Это даёт технике основу для «ворот силы» из наблюдения владельца (09.11): чтобы копать в новом
пласте быстро, нужна кирка посильнее; после перерождения ранние пласты пролетаются за секунды. Решение за геймдизайном.

### 1.7 Сохранение (DataStore)

**Простыми словами.** Шахта игрока весит в сохранении несколько килобайт — меньше, чем инвентарь. Сохраняется вместе с
профилем, тем же надёжным механизмом, что в «Каторге».

```lua
p.mine = {
	v = 1, seed = 123456789, w = 5, h = 3, front = 4312,
	top = "…",    -- строка: base64 от буфера varint (дельты от front) по дорожкам
	holes = "…",  -- строка: для каждой дорожки — число отрезков, затем пары (зазор от предыдущего, длина) varint
}
```

- Размер: при 4 000 отрезках ≤ ~20 КБ, обычно < 2 КБ. Профиль целиком — цель < 100 КБ (лимит ключа DataStore ≈ 4 МБ
  [devforum, см. источники]).
- Кодирую в строку base64, а не в `buffer` прямо: сообщения сообщества говорят, что DataStore принимает buffer, но
  официального подтверждения я не нашёл [не проверено] — строка надёжна и читается в DataStore Manager.
- `MineState.decode` проверяет все инварианты (как `Mine.restore` прототипа); битое сохранение → загрузка не удалась →
  правило старой игры: профиль с `loadFailed` никогда не сохраняется.
- Автосохранение каждые 120 с, при выходе, при закрытии сервера; блокировка сессии `_lock` (против дюпа на аукционе) —
  всё из `ProfileService` старой игры.
- Название хранилища новое (`Profiles_v1` в новом experience); схема — с полем `v` и миграциями.

## 2. Сервер и клиент: кто что считает, протокол

**Простыми словами.** Телефон ребёнка присылает серверу только «я ударил вот сюда». Сервер проверяет, мог ли он туда
ударить и не слишком ли часто, считает всё (какие блоки сломались, полетела ли молния, что нашлось, сколько денег) и
отвечает одним коротким сообщением. Телефон проигрывает это красиво: трещины, молнии, «+12 540 $», езду стены. Чтобы
не было задержки после нажатия, телефон сразу ломает «обычную» форму удара сам, а сервер через 0,1–0,2 с подтверждает
и добавляет молнии и находки. Обмануть нельзя: деньги и шансы живут только на сервере.

### 2.1 Разделение

| Сервер (`MineService`, `HitService`, `ProcService`, `EconomyService`) | Клиент (`src/client/Mine/*`, `Fx/*`) |
|---|---|
| состояние шахты, зерно, генерация | окно из 20 слоёв: какие клетки целые и что в них (от сервера) |
| проверка намерения: темп, клетка, расстояние, заряд ульты | прицел, ввод (тап/зажим/авто), предсказание базовой формы |
| форма удара, урон, «крепость» | трещины, звук удара, частицы |
| фишки (молния, взрыв, лёд …): шансы с псевдослучайным распределением, каскады ≤ 3 поколений | анимация каскада по «сценарию» от сервера, свет, гром, цепь разрядов |
| подсчёт руды (`rangeHist`), деньги, ключи, находки, задания, топы | сумма у точки удара, барабан цифр |
| `advance()`: сдвиг фасада | езда стены, линии скорости, FOV, тряска |
| события (Золотая жила, Лихорадка, Разгон) — таймеры и множители | музыка по слоям, подсветка «последних 3 блоков» |

### 2.2 Сообщения (RemoteEvent с `buffer`)

Все пакеты — `buffer` (как `src/shared/MineNet.luau` старой игры): компактно, без проблемы «таблица режется на nil»
(`Wire.luau`). Модуль `src/shared/Mine/MineWire.luau` пишет и читает их на обеих сторонах.

Клиент → сервер (надёжный `RemoteEvent "MineIntent"`):

| Сообщение | Поля | Частота |
|---|---|---|
| `Hit` | `u16 seq, i8 x, u8 y, u8 dRel` (глубина от фасада, 0…19) | ≤ темпа кирки, на практике ≤ 10/с |
| `Ability` | `u16 seq, i8 x, u8 y, u8 dRel` | когда полоса заряда полная |
| `Resync` | — | после потери связи / несовпадения |

Сервер → владелец шахты (надёжный `"MineResult"`):

```
u16 seq | u8 flags(accepted, rideFollows, …) | u32 front
u16 nCells   × (i8 x, u8 y, u8 dRel, u8 gen)          -- удалённые клетки В ОКНЕ (поколение: 0 = удар, 1–3 = каскад)
u8  nRuns    × (i8 x, u8 y, u32 a, u32 len)            -- удалённые «прогоны» глубже окна (разлом, ульта)
u8  nEvents  × (u8 kind, u8 gen, u16 delayMs, u8 nPts, pts…)  -- сценарий эффектов: путь молнии, центр взрыва, лёд…
f64 money | f64 logicalBlocks | u8 nFinds × (u8 kind, u16 id)
[если фасад сдвинулся] u32 delta + окно новых слоёв: для каждого слоя маска целых (до 105 бит) + тип руды 1 байт на целую клетку
```

Размер: обычный удар 20–60 байт; каскад на сотню клеток ≈ 0,5 КБ; полное новое окно 20 × 45 клеток ≤ ~1 КБ. Надёжный
канал, потому что потеря = рассинхрон.

Сервер → все на сервере (`UnreliableRemoteEvent "MineFx"`, пачкой раз в 0,1 с): `u8 plot, u8 kind, i8 x, u8 y, u16 size`
— для соседей (2.5). Лимит пакета ненадёжного события по документации — 900 байт [create.roblox.com, см. источники];
пачку режем по 800 байт.

### 2.3 Проверки на сервере (анти-чит)

```lua
function HitService.onHit(player, seq, x, y, dRel)
	local s = sessions[player]; if not s or s.busy then return end
	if not s.bucket:take(Time.now()) then return end        -- ведро токенов: запас 3, пополнение раз в interval кирки
	if typeof(x) ~= "number" … then return end               -- тип/диапазон (MineWire уже гарантирует)
	local st = s.mine; local lane = laneKey(x, y)
	if not st:inWall(x, y) or dRel >= WINDOW then return reject(seq) end
	local d = st.front + dRel
	if not st:isSolid(lane, d) or not st:isExposed(x, y, d) then return reject(seq) end  -- видна ли клетка игроку
	if not Plots.onOwnPlatform(player) then return reject(seq) end                     -- стоит на своей площадке
	local res = Resolve.hit(st, s.profile, s.rng, x, y, d)    -- форма → урон → фишки → каскады (бюджет) → hist
	Economy.grant(player, res)                                -- ProfileService.Mutate; накопители ключей; задания
	res.delta = st:advance()
	MineWire.sendResult(player, seq, res)
	FxRelay.push(s.plot, res.summary)
end
```

- «Видна» (`isExposed`): клетка на фасаде или у неё есть пустой сосед (в том числе ближе к игроку). Через пробитую
  дыру можно бить вглубь — это и есть «куда бить» (PLAN п. 12).
- Автокликер не даёт преимущества: темп ограничен сервером ровно темпом кирки. «Авто-копание» стоит сделать честной
  функцией игры, чтобы дети не искали кликеры (решение геймдизайна, техника готова).
- Шансы фишек — псевдослучайное распределение (PRD, PICKAXES п. 3) с состоянием на сервере; бюджет каскада:
  ≤ 3 поколений, ≤ 400 клеток окна и ≤ 8 прогонов за удар [решение] — иначе один удар грузит сервер и ломает экономику.
- Ошибки молча отвергаются (`reject(seq)` → клиент возвращает предсказанные блоки), никаких киков за «быстро».

### 2.4 Предсказание и задержка

Клиент сразу (в тот же кадр) показывает трещину, звук и **удаление базовой формы** (её можно вычислить без шансов: форма
кирки + окно). Клетки помечаются «ждём»; ответ сервера заменяет предсказание полностью: лишние вернуть (редко), каскад
проиграть по `delayMs`. Сумму денег показываем по ответу сервера — через 100–200 мс, на глаз это «сразу после
удара». Если `seq` ответа не совпал с ожиданием → `Resync` (сервер шлёт окно целиком).

Езда стены: сервер сдвигает фасад мгновенно; клиент анимирует 0,35–1,6 с (`0.35 + 0.25·log10(delta+1)`, [решение]).
Во время езды удары разрешены — логические координаты клеток уже новые, рендер просто ещё «доезжает».

### 2.5 Пять человек и чужие шахты

**Простыми словами.** У каждого своя шахта, войти в чужую нельзя. Но соседей видно: их молнии, взрывы, «гиперпрыжки»,
цифры над головой. Это дешёвые сообщения «у соседа №3 взрыв размером 40», без пересылки его блоков.

- `PlotService` раздаёт 5 площадок-тоннелей при входе (атрибут игрока `Plot = 1…5`). Чужая площадка закрыта
  невидимой стеной; удары по чужой шахте сервер отвергает (`onOwnPlatform`).
- Варианты раскладки (решает художник уровня; технически годятся оба):
  **А** — 5 тоннелей веером из общего зала (лобби), каждый игрок видит устья соседей; **Б** — тоннели рядом через
  стенку с «окнами». В обоих случаях чужую стену клиент рисует **упрощённо**: первые 6 слоёв, без трещин и частиц
  (сервер шлёт соседям маску 6 слоёв ≤ 300 байт не чаще 2 раз в секунду и только при изменении).
- Эффекты соседей — из `MineFx`: молнии/взрывы облегчённые (меньше частиц), гиперпрыжок соседа — вспышка в его тоннеле.
- Объявления на сервер (легендарная кирка, рекорд глубины) — обычные надёжные события, редкие.
- Бюджет репликации на одного игрока [решение, проверить замером]: своё ≤ 3 КБ/с в среднем, пики до ~10 КБ/с на
  каскадах; соседи ≤ 4 × 0,5 КБ/с; персонажи — стандартная репликация Roblox. Блоки шахты — 0 (они локальные).
- Общие цели сервера (общий бур, общий босс-стена — пробелы PLAN) ложатся на тот же канал: сервер суммирует вклад
  пяти игроков, клиентам — одно число раз в секунду.

## 3. Производительность на телефонах

**Простыми словами.** Слабый телефон тормозит не от «много денег», а от того, сколько всего рисуется и сколько разных
картинок в памяти. Поэтому: рисуем только блоки, которые видно; переиспользуем одни и те же детали вместо создания
новых; у всех блоков одна форма куба и мало разных текстур; эффекты и частицы — с жёстким лимитом и с режимом «меньше
эффектов». Цель — ровные 60 кадров на среднем телефоне и не ниже 30 на слабом.

### 3.1 Что нашёл о рекомендациях Roblox (поиск 09.11.2026)

`create.roblox.com` и `devforum.roblox.com` из сети этой сессии не открываются (страницы не прочитаны полностью) —
ниже выводы по поисковой выдаче; цифры сообщества помечены как неофициальные.

- Официально: на слабых телефонах главная беда — нехватка памяти и вылеты (OOM); эмулятор Studio для памяти
  непоказателен — тестировать на настоящем телефоне; встроенные материалы занимают намного меньше памяти, чем свои
  текстуры; стриминг — главный рычаг памяти. [create.roblox.com «Design for performance»]
- Рисование: детали с одинаковым мешем, материалом и текстурой собираются в пачки (instancing) — меньше draw calls;
  каждая наклейка (Decal) на грань — отдельный draw call; каждый ParticleEmitter — минимум один draw call.
  Ориентир сообщества — до ~500 draw calls в кадре [devforum, неофициально]. Цель мобильных игр — 30 FPS минимум
  [блог, неофициально].
- `workspace:BulkMoveTo` выигрывает у присвоения CFrame по одной от ~50–100 деталей; лучше — закреплённые детали без
  столкновений и без режима, который стреляет событиями [devforum, неофициально].
- `UnreliableRemoteEvent`: 900 байт на пакет; ~500 вызовов в секунду на клиента на все события одного типа [документация].
- Roblox выпустил стриминг текстур (2025–26) [devforum «Introducing Texture Streaming»].

### 3.2 Блоки

- **Пул** `src/client/Mine/BlockPool.luau`: заранее 1 000 закреплённых деталей (`Anchored`, `CanCollide = false`,
  `CanQuery = true` только для прицела, `CastShadow = false`), выдать/вернуть без `Destroy`. Обычно на экране
  100–400 блоков: рисуем только клетку, у которой есть открытая грань (фасад + стенки пробитых дыр) — как
  `MineService` старой игры («Parts only for blocks with an exposed face»).
- **Форма и текстура:** один `MeshPart`-куб с UV-развёрткой, текстура на руду (`TextureContent`), все грани одинаковые.
  Одинаковые меш+текстура → движок собирает их в пачку. Не используем Decal на 6 граней (×6 draw calls).
  Вариант «Part + MaterialVariant» (старый конвейер `px_*`) — **проверить в этапе 2**: если текстура материала
  «плывёт» при езде стены (проекция по миру, а не по детали), он не годится [не проверено].
- Текстуры руды: пиксель-арт 16×16, увеличенный ближайшим соседом до 128×128 (иначе размылится — тот же приём ×8, что в
  `scripts/prepare-voxelibre.ps1`). На пласт ≤ 10 текстур, в памяти ≤ 2 пласта одновременно (текущий и следующий).
- **Езда стены:** все блоки окна двигаются одним `workspace:BulkMoveTo(parts, cframes, Enum.BulkMoveMode.FireCFrameChanged)`
  — заменить на режим без событий, если замер покажет выгоду. До 1 000 деталей в кадр — по замерам сообщества это
  доли миллисекунды, но бывают пики; запасной план — сварить блоки окна с одним «корнем» и двигать только корень.
- Пройденные пустые слои **не рисуются** (их нет). Бесконечность тоннеля — повторяющиеся модули стен/ламп по 4 слоя,
  которые «прокручиваются» по модулю (8 модулей в пуле) + туман `Atmosphere`/`Fog` с ~14-го слоя.

### 3.3 Эффекты

| Эффект | Как | Лимит [решение] |
|---|---|---|
| Молния | пул `Beam` (ядро + широкий полупрозрачный ореол, `LightEmission = 1`), ломаная из 6–10 вершин, яркость анимируется; форма один раз на удар | ≤ 48 сегментов одновременно |
| Вспышка/гром | `ColorCorrection.Brightness` на 0,1 с + звук; не настоящие лампы | ≤ 2 `PointLight` (свет ламп тоннеля) |
| Частицы ломки | пул из 6 `ParticleEmitter` с `:Emit(n)`, а не эмиттер на блок | ≤ 1 500 частиц всего, ≤ 300 на «Мало эффектов» |
| Цифры «+$» | пул `BillboardGui` | ≤ 12 одновременно |
| Скорость (езда) | FOV +10–15°, линии — `ImageLabel` в `ScreenGui`, не 3D | — |
| Соседи | облегчённые версии тех же эффектов | ≤ ¼ своих |

Настройка «Меньше тряски и вспышек» и автоматическое снижение (если 3 с подряд FPS < 40 → уровень эффектов ниже).

### 3.4 Цели и как мерить [решение]

- Кадры: 60 FPS на среднем телефоне, ≥ 30 FPS на слабом (взять 1 бюджетный Android и 1 старый iPhone как эталон;
  владелец/тестеры называют модели).
- Draw calls в шахте ≤ 300 (счётчик сцены Ctrl+Shift+F2), деталей шахты на экране ≤ 600, частиц ≤ 1 500.
- Память клиента: замер на эталонном телефоне через консоль разработчика; бюджет текстур игры ≤ 40 МБ [решение].
- Сервер: разбор удара ≤ 1 мс в среднем, ульта ≤ 15 мс (иначе разбить на кадры).
- Инструменты: MicroProfiler, Developer Console (Memory, Network), `scripts/qa-studio-render-state.luau` из старой игры.

(тесты Codex и симулятор), без Studio. В `rokit.toml` добавить `lune-org/lune` (взять актуальную стабильную версию).

## 5. Порядок работ для Codex

**Простыми словами.** Сначала собираем маленький, но настоящий кусок игры, в который можно поиграть на телефоне: одна
шахта, одна кирка, деньги, езда стены, молния. Если это приятно — наращиваем. Если нет — меняем дёшево, пока кода мало.
Каждый этап заканчивается проверкой, которую понятно провести (что нажать, что должно произойти).

Объём — в «днях Codex» (одна сессия ≈ одно ТЗ + проверка Claude) [оценка].

| # | Этап | Готово, когда (критерии приёмки) | Объём |
|---|---|---|---|
| 0 | **Каркас.** Новый репозиторий, перенос инфраструктуры 4.1 (профили, конфиги, строки, Remotes, реле, CreativeService, ServerLog), Lune, линтеры | `rojo build` проходит; `selene`, `stylua --check`, `lune run tests` зелёные; в Studio профиль грузится и сохраняется, повторный вход видит данные; ни одного файла из 4.2 | 2–3 |
| 1 | **Ядро шахты (без Studio).** `MineGen`, `MineState`, `Shapes`, кодирование сохранения | тесты: (а) `rangeHist` = перебору по клеткам на 10 000 случайных отрезков; (б) инварианты после 100 000 случайных операций; (в) «передний слой не пуст — не едем»; (г) проезд 101–103 → 104 одним `delta`; (д) пустота на 5 000 сохраняется после езды; (е) encode/decode туда-обратно, битые данные отвергаются; (ж) ульта 5 000 × 15 в Lune < 5 мс, затем замер в Studio | 2–3 |

решает по ощущению, двигаемся ли дальше так же.

### 5.1 Риски и как их снять

| Риск | Чем опасен | Как снимаем |
|---|---|---|

## 6. Конфиги и баланс

**Простыми словами.** Все числа игры (цены, шансы, силы кирок, пласты) лежат в одном файле решений. Скрипт превращает его
в аккуратные файлы для игры и проверяет ошибки (например, что доли руды в пласте дают 100 %). Отдельная программа
«проигрывает» игру за виртуального ребёнка тысячи раз и показывает: через сколько минут новая кирка, новый пласт,
первая легендарная — и где игроку скучно (слишком долго до следующей цели).

Правила (как в старой игре): **сгенерированный** `src/shared/Config/*.json` руками не правим; каждое число в документах —

### 6.2 `scripts/build-configs.mjs`

Оставляем механизм (чтение решений → запись `Config/*.json`, компактная запись больших файлов, лимит ModuleScript
200 000 символов), выкидываем всё чтение `wiki/` «Каторги». Добавляем **проверки, которые роняют сборку**:
Σ долей руды пласта = 1 ± 1e-9; `segment` делит `stratumLen`; у каждой кирки семья и редкость существуют; у каждого
`id` есть строки `item_<id>` во всех языках; цены растут монотонно; шансы ≤ 1 на максимальном уровне; `maxGen ≤ 3`.

### 6.3 Симулятор экономики

`scripts/simulate-economy.mjs` старой игры моделирует «копать уровень → продать → купить инструмент» по формулам на
JavaScript — для новой игры не подходит (нет слоёв, каскадов, событий) и дублирует логику. Новый симулятор:

- **`scripts/sim/economy.luau`, запуск `lune run scripts/sim/economy -- [минут] [прогонов] [модель]`**. Он `require`-ит
  настоящие `MineGen`, `MineState`, `Resolve`, `Procs`, `Economy` из `src/shared` (без Roblox API) и конфиг из JSON.
- Модели игрока: «тапер» (3–4 удара/с, бьёт в лучшее место по простому правилу), «авто» (темп кирки), «редко заходит»
  (сессии по 10 мин раз в день). Покупает жадно: следующая кирка / самая дешёвая полезная карточка / ширина стены.
- Монте-Карло: 200 прогонов с разными зёрнами шахты и RNG.
- Отчёт (markdown + CSV в `docs/new-game/sim/`): минута первой молнии, каждой кирки, пласта, первой редкой/легендарной;
  деньги/мин и блоки/мин по времени; частота срабатываний фишек и ульты; **«самый длинный разрыв до следующей цели»**
  по минутам — проверка «трёх частот наград» из RESEARCH-DOPAMINE (флаг, если в первый час разрыв > 5 мин [решение]);
  доля денег от каскадов, бустеров, Лихорадки (флаг, если одно даёт > 60 %).
- Запускать после любой правки баланса (как правило старой игры). Ускорение: симулятор пропускает анимации и считает
  удары пачками; цель — час игры × 200 прогонов < 1 минуты.

## 7. Открытые вопросы владельцу и студии

1. Раскладка 5 тоннелей: веер из общего зала (видно соседей) или тоннели через стенку с окнами? (2.5)
2. Есть ли в новой игре фракции/команды? От этого зависит бустер «фракционный» (BRIEF: 2+2+2 = ×6).
3. «Крепость» пластов (ворота силы, 1.6) — нужна ли, или каждый блок всегда ломается одним ударом?
4. Авто-копание: бесплатно для всех, с уровня, или как геймпасс (честно ли это для детей — решает геймдизайн)?
5. Языки: оставить ru/en/es/fr или добавить португальский/другие (аудитория Roblox-детей)?
6. «Твоё место» за пределами топ-100: достаточно «100+ · до топа не хватает X» или нужна оценка номера?
7. Перерождение: новое зерно шахты и фасад с нуля — подтверждаем (технически это дёшево)?
