# Profile shutdown and late top-board replication

Parent observed an owner kick after ordinary cloud Play stop/start: the profile was still locked, although no other Studio server was expected. This agent did not inspect/mutate the owner's record, use Studio or bypass the lock. The following deterministic source races are consistent with that symptom; no trace of the prior shutdown exists to prove which write actually remained outstanding.

## Confirmed races and corrections

**Detached final save was invisible to shutdown.** The old `PlayerRemoving` callback removed `sessions[player]` before waiting for an autosave or yielding in its final UpdateAsync. `BindToClose` counted only entries still in `sessions`. If leave had already detached the last session, shutdown returned without awaiting that release. `ProfileService.beginRelease` at line 559 now registers the exact session in `closingSessions` before detaching or yielding, deduplicates the final worker through `session.closing`, waits for its in-flight save, and removes the pending entry when the worker settles. Both lifecycle callbacks use it. `BindToClose` at line 1250 starts remaining active profiles and drains the shared registry, including releases begun by earlier leave callbacks. Reversed callback order and multiple profiles are covered.

**Acknowledged durable data could be rolled back by the final save.** During `MutateDurable`, a leave could detach the session while UpdateAsync persisted the staged transformation. The old post-save session-identity check then returned false before updating that session's live profile. Its final save persisted the old values over the acknowledged checkpoint. Now the successful synchronous transformation is applied to the detached session before the identity check (`ProfileService.luau:624`). The departed caller still receives false and cannot rely on this call to export a reward; the final write preserves the already-confirmed checkpoint. Failed checkpoints do not apply the transformation. Exact job/token ownership checks, acquisition waits, TTL, store selection and save validation are unchanged.

**Late `Tops` warning and missing later subscriptions.** `TopBoards.Start` already put its WaitForChild in a spawned task, so this warning did not block main client initialization. Its one-time child scan could nevertheless miss board values replicated after the folder. `TopBoards.luau:284` now subscribes to the real folder's arrival and its later StringValues before scanning existing children; each value has one change listener and triggers a refresh on arrival. No placeholder folder is created and no actual leaderboard fetching/rendering is suppressed. Wrong-class/unrelated children are ignored.

The pending registry waits for completion; it cannot make an unavailable store, forced process termination or engine shutdown deadline acknowledge a write. A failed release retains the normal lock behavior rather than pretending another server can safely take over. In-flight acquisition before a session has been installed is a separate existing lifecycle path, outside these two proven final-save races. Native acceptance remains parent's ordinary join, stop/start after a loaded profile, and verification that late leaderboard data updates; this report does not claim that live rerun passed.
