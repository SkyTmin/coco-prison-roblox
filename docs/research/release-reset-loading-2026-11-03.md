# Full gameplay reset and initial loading

Owner follow-up on 2026-11-03: their own explicitly confirmed Creative reset left two ancient stars in personal storage, 23 keys and 16 toilet-paper items in the bag. This implementation was verified only with isolated negative simulated profiles. The reviewer did not operate Studio, reset the real owner, commit or publish.

## Reset cause and correction

The previous `ProgressReset.apply` deliberately retained any stack whose ID appeared in `Config.donate.items`, plus booster items, without knowing whether the stack was bought or earned. That explains the reported consumables surviving in both bag and ender/vault storage. It also omitted `stash`, stored/active personal boosters and settled gift/auction overflow. The owner's clarification supersedes that conservative item-retention policy.

Reset now replaces the complete bag with the default starter shovel and clears armor, every ender/vault slot, every case-content table (including ancient overflow), stash, stored/active personal boosters, settled gift overflow, auction returns and page mirrors. Existing progression/stat/achievement/tutorial reset remains. There is no separate saved-inventory cache in current production services; serialized inventory is generated from the reset profile on the same durable save. Shared faction/gang storage remains shared property and is not erased. Pending external operations and gang membership still block reset rather than abandoning another account's journal.

Persistent paid entitlements remain: premium currency balances, purchase receipts, consumed permanent perks such as autosell/no-needs/passes, unlocked vault/auction capacity, PRIS+ expiry, settings and access. Purchase provenance does not exempt physical consumable stacks anymore. Receipt IDs, boss reward cooldowns/receipts, general operation IDs, daily/referral anti-repeat records and unknown lock fields remain intact. The four-language warning explicitly distinguishes deleted purchased consumables from retained activated entitlements.

External player-transfer recovery now has a recipient generation. Submit snapshots the recipient's current generation without yielding; the durable reset increments it. A pre-reset or legacy packet delivered after reset receives a durable permanent receipt but no grant, then acknowledges normally so the sender can settle. This covers an old outbox that was not posted until after reset as well as a mailbox entry already posted before reset. New-generation transfers work normally. Reset intentionally forfeits old outstanding incoming value; it does not refund the sender or replay purchases. Active incoming/outgoing journals already installed in the profile still prevent reset. A failed or uncertain reset keeps the existing quarantine/rejoin behavior.

## Early loading screen

`default.project.json` now maps `src/first` to `ReplicatedFirst.Loading`. The existing sync generator walks this mapping and emits the Bootstrap LocalScript and its three modules; no hardcoded sync change is needed. The early screen builds its own dark, orange-header, Code-font UI before removing Roblox's default loading screen. It has native-sized text/48px retry, top-inset-safe layout, and a scrolling panel for short landscape viewports. Its small four-language catalog lives beside it in ReplicatedFirst so early rendering does not wait for Shared/Config.

The checklist reflects five actual facts, not estimated percentages: main client initialization; a successful profile snapshot; live character at its server-confirmed restored arrival; actual nearby streamed collision; completion of the small critical-image fetch set. A default profile produced after a failed DataStore load carries `loaded=false` on ProfileUpdated and cannot unlock the screen merely because some profile table exists.

ProfileService exposes `ProfileState` and stamps the current character's `ArrivalPosition`/`SpawnReady` only after the existing saved-position restoration. Concurrent restoration callbacks are guarded so an early second callback cannot announce spawn readiness while the first is still streaming. `ClientBootstrap` is throttled and resends a fresh initial snapshot if the original arrived before the HUD connected. A failed profile load can retry its exact acquisition token; this avoids conflicting with its own lock after an applied-but-error acquire, and never saves the fallback default profile.

The client requests streaming at its actual current arrival, then raycasts local collision beneath the character. It does not require a distant map folder, all named locations, or every mine to replicate. The asset list is bounded to at most 32 typed hotbar/current-nearby Instances from at most 96 nearby parts; map preview catalogs and whole Workspace are not preloaded. The real HUD ImageLabel/ImageButton is preferred; missing HUD consumers get a temporary ImageLabel cleaned after the attempt. Nearby Decal/Texture/MeshPart objects retain their specialized engine loading path. MaterialVariant textures continue normal engine streaming. This establishes essential arrival readiness, not a claim that every decorative texture in a streaming world has loaded.

Independent review identified two additional races, now corrected. A mine/world-safety rescue can move the character before the original arrival is observed, or during asset fetch. The throttled bootstrap can restamp the current authoritative root only after initial restoration is complete; scene work is invalidated after displacement, and the actual current floor is rechecked after fetching and before release. The parent also added `workspace.RuntimeReady` at the end of server startup; interface readiness requires both this authoritative handler-ready flag and the completed client init hook. Separately, a confirmed reset records its old character in an ephemeral session guard: the five-second position recorder and leave path cannot refill cleared lastPosition from that body while Creative's replacement character is still loading.

Before main initialization, a high-priority movement action, modal input shield and render guard block movement/jump. Main WindowInput also blocks gameplay intents and owns controls/camera while `LoadingBlocked` is true; windows cannot open through `open()` during initial loading. After all facts pass, the screen and early guards are removed and WindowInput restores normal ownership (or keeps a menu's ownership). Timeout/fetch/profile failures show a retry action and retain the block. Retried asynchronous work is generation-guarded; an older stream/asset response cannot complete a newer attempt. This loader covers initial entry; it does not pretend to load the entire world again on every ordinary respawn or location teleport.

### Live preload blocker and confirmed fix

Parent's full-sync client reached ProfileState/RuntimeReady/SpawnReady but stayed at asset_error. Live A/B showed existing visible hotbar ImageLabel (`IsLoaded=true`) succeeded when passed as an Instance, while the same image's raw ID string failed. A new location illustration behaved the same way. Typed ImageLabel preloading subsequently passed **30/30** uploaded location illustrations; evidence is `release-art-preload-2026-11-03.json`. This isolates the blocker to the API input path, not inaccessible uploaded art. The production loader now uses typed Instances and retains the mandatory success gate. Local attributes LoadingAssetCount, LoadingAssetSucceeded and LoadingAssetFailures expose bounded diagnostic evidence. Final ordinary-join acceptance after this source correction belongs to the parent.

This behavior matches Roblox engineering guidance: [specialized Instance loading instead of strings](https://devforum.roblox.com/t/1637450/25) and [2026 ImageLabel preload/memory clarification](https://devforum.roblox.com/t/4039525/16). Typed success is not misreported as every hidden image being rendered; unused hidden textures may later be evicted. Reusing the actual HUD consumers avoids unnecessarily creating then abandoning an image consumer.

Official API guidance: [Roblox loading screens](https://create.roblox.com/docs/players/loading-screens) and [ReplicatedFirst](https://create.roblox.com/docs/reference/engine/classes/ReplicatedFirst) support keeping early dependencies local and removing the default screen only after creating a replacement. [ContentProvider](https://create.roblox.com/docs/reference/engine/classes/ContentProvider) documents fetch status callbacks, unsupported MaterialVariant preloading and avoiding RequestQueueSize-based progress. [Player streaming request](https://create.roblox.com/docs/reference/engine/classes/Player#RequestStreamAroundAsync) is a request, so this loader separately verifies actual local collision.
