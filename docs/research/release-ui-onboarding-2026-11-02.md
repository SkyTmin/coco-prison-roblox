# Release UI, actions and onboarding

Implementation/isolated verification completed 2026-11-03 for the owner's 2026-11-02 release request. No Studio operation, real-owner reset, real invite, commit or publish was performed by this reviewer. Parent owns Studio acceptance and final integration. All stated numbers below describe implementation or measured test results, not gameplay balance claims.

## Previous behavior

- No persisted first-login mine → sell → item-upgrade guide existed. Spawn already provided a level-one shovel and the main prison mine.
- `/pay`, `/gift` and `/hide` existed, but their command path and feedback depended on chat. Player-card shortcuts did not provide the requested mobile recipient/item/count review workflow.
- Creative offered temporary test mode, grants and inventory clearing, but no separately confirmed own-progress reset. Ancient books were not grouped under every compatible item type.
- Existing profiles must not unexpectedly replay onboarding. Paid purchases and repeat-reward protections must survive an intentional gameplay reset.

## Implemented behavior

### Server-owned tutorial

`src/shared/Tutorial.luau` defines three ordered steps and completion. New `ProfileService.defaultProfile()` records start at mining; existing schema-v3 records without a tutorial migrate to completed/legacy. Completion is profile state, not a client flag.

`TutorialService` advances only from actual service outcomes: `DigService` supplies a successfully delivered main-prison-mine drop; `EconomyService.sell` supplies the amount of that particular resource removed by the actual sale; successful item upgrade supplies before/after item levels. Wrong mine, zero delivery, unrelated sale and unsuccessful upgrade do not advance. Existing paid autosell can complete the sale as part of the actual mining result. Each real transition schedules `SaveNow`; normal profile autosave/rejoin remains the persistence mechanism if a checkpoint fails. There is no remote accepting tutorial completion from clients.

`TutorialGuide` renders localized progress, a world arrow and local highlight on a nearby shovel-compatible main-mine cell, then the nearest seller. It highlights the seller's Sell button and later menu/Upgrade buttons, with a direct upgrade shortcut. It hides its instruction card while another menu is open and removes obsolete highlights on a step change. Existing profiles remain unobstructed.

Integration: `ProfileService` default/migration, `DigService` outcome, `EconomyService` sale/upgrade, parent-owned server startup, and `init.client` guide startup. The guide does not alter progression costs or award a synthetic completion reward.

### Actions without chat input

The main menu and mobile menu now expose Actions. `ActionsWindow` supports money transfer, an explicitly chosen inventory slot and count, hiding/showing players, and the platform's native invite prompt. Recipients show both display name and canonical username. Review displays the exact recipient and quantity; a separate Send button submits confirmation; the result appears inside the window.

`ActionsService` creates a short-lived, single-use server quote and snapshots all selected item metadata. Confirmation resolves the original connected UserId, consumes the token first, and invokes the same authoritative `ChatCommandService` pay/gift/hide path. It retains source/recipient availability and export gates, recipient preferences, finite/integer validation, item restrictions, location/range/gang checks and capacity checks. A changed stack requires a fresh review. Canonical usernames take priority over another player's spoofed display name. Simulated negative-ID Studio players are supported only when they resolve to an actual connected Player; unknown IDs still fail.

Gift now supports an explicit partial quantity while preserving the full stack metadata. Old `/gift name` still uses the entire held stack. Sender result capture is structured for Actions; existing recipient notifications and chat command behavior remain available. Quoting has no inventory/currency side effect; duplicate confirmation cannot transfer twice.

`ActionsWindow`, Creative and Reset use native pixel layouts with maximum sizes rather than shrinking a desktop form. Actions controls are at least 44 pixels high, inventory choices 48 pixels, text entries 16 pixels and principal action text 14 pixels. Scrolling retains a usable form row at the tested 390×844 portrait and 844×390 landscape geometry. Stable `Action*` names support test instrumentation.

The invite helper optionally obtains the server's opaque `ServerInviteRoute` ticket and passes it through `ExperienceInviteOptions.LaunchData`; a missing/failing route still permits the existing native prompt. No invite is sent by tests. API references: [Roblox invite prompts](https://create.roblox.com/docs/production/promotion/invite-prompts), [VirtualInput mouse/keyboard QA API](https://create.roblox.com/docs/reference/engine/classes/VirtualInput). VirtualInput mouse automation is not a touch test.

**Durability defect found and corrected:** the old shared `/pay` and `/gift` implementation saved sender and receiver sequentially without checking the sender result, allowing duplicated value after a partial save. Root treated this as a release blocker. New `PlayerTransferService` is the single transport behind `/pay`, `/gift`, Actions and the equally affected `/rubb`. It records the debit and immutable outbox in the source profile and confirms that save before publishing a per-recipient durable mailbox entry. The recipient writes receipt plus grant together through the actual `ProfileService.MutateDurable` boundary. Permanent receipts prevent old mailbox entries, retries and post-reset replay from granting twice. Only an acknowledged mailbox completion permits durable sender-outbox cleanup.

Pending source/incoming journals close export and destructive-reset gates; root also integrated them into storage/death/boss busy recomputation. A failure before an initial source save commits cannot credit the recipient; the pre-transfer balances survive a crash. An applied-but-error source or receiver write retries from the persistent journal. A recipient on another server or returning later discovers their durable mailbox independently. The source stays pending until recipient delivery is acknowledged. There is no promise that a request not yet durably saved will survive a server crash: the pending message explicitly waits for confirmation.

Gifts credit an exact immutable stack to a private durable gift queue together with the receipt, then move inside that single profile into available bag space. This fixed destination preserves all metadata through a full bag and never rerolls an item. A remainder is auto-claimed when space appears or manually through Actions → Collect received gifts. Settled unclaimed gifts are discarded by an explicitly confirmed gameplay reset; active transfer journals still block it. Sender and receiver receive localized pending/completion/collection feedback. No client transfer retry is needed while the server journal is pending.

### Explicit own-progress reset

Creative displays Reset only for the configured owner/admin or actual user place creator. Studio's blanket Creative permission does not grant reset permission. The server accepts no target user: it can reset only the sender. The first screen lists deleted and preserved data; Continue obtains a server nonce, then a separate final confirmation names the current account and explains irreversibility. Tokens are short-lived and single-use. Closing/reviewing alone does not delete data.

`ProgressReset` resets level, ordinary money, all personal items/equipment/containers, stash/boosters/claim queues, mining/progression counters, achievements, professions, artifacts, skills, trainer upgrades, nicknames, faction, survival state and saved location. It restores a starter shovel and tutorial step one. **Owner correction 2026-11-03:** purchased consumable stacks are also deleted; the old catalog exemption caused the reported leftover keys, toilet paper and stars. Premium currencies, receipts, activated permanent paid perks, settings, unlocked capacity/access, operation IDs and reward cooldowns remain. A recipient generation prevents delayed old mail/outboxes restoring discarded assets. See [full reset/loading correction](release-reset-loading-2026-11-03.md) for the authoritative behavior and newer 297/120/82-check results.

Reset refuses pending storage/death/boss-reward/player-transfer operations, unclaimed player gifts, shared booster/gang/announcement operations, active gang membership, and unsettled auction lots/returns. It preserves `bossRewardUntil`, `bossRewardReceipts`, permanent player-transfer receipts, other dynamic protection fields and session acquisition identity. `CanExport` now also closes on `bossRewardPending` and both player-transfer journal fields; parent updated shared busy recomputation accordingly.

`ProfileService.ResetOwnProgress` uses the actual durable transformed-save boundary. During persistence it freezes normal mutations/exports and saved-position recording. The new state is published only after acknowledgement; an uncertain write quarantines the old live profile and requires rejoin, because the reset may already have been applied. Successful reset is not treated as a new account for referral rewards. Creative respawns the confirmed sender at the normal spawn; the persisted tutorial restarts on rejoin too. No owner's real profile was reset to prove this.

### Creative book catalog and integration

`CreativeBooks.groups` generates separate compatible-item groups, highest rarity first, then localized name and stable ID. Multi-target books appear in every supported group, with their available levels. Existing give validation and item metadata construction remain in CreativeService. Top actions and tabs reflow into readable rows on narrow screens.

`init.client` also wires the economy agent's `SpringJump.start()` and the parent's HurtFeedback health display API/Changed signal. Read-only review of HurtFeedback/EffectsHud found no current blocking issue: character/id guards, coherent health/absorption, victim broadcast exclusion and separate book impulses agree with the integration. These modules assume the current singleton ScreenGui lifetime; they are not designed to restart after arbitrary GUI destruction. Physical timing remains the parent's live PvP acceptance.

## NPC prompt localization checkpoint

The actual NPC ProximityPrompt properties previously used the server's default Russian text even after a player changed language. `PromptText.Set` now writes a single JSON metadata attribute per text property containing the exact translation key and typed arguments, plus the canonical Russian fallback. Narrow constructor/update integrations cover Economy, Location, Needs, Case (including changing case identity), Daily/canteen, GangBase, GangHouse, Ghetto and GhettoMine. Dynamic member counts, minutes, counts and multiplier strings remain their original arguments; there is no reverse parsing of formatted text.

`PromptLocalizer.Start` is wired in `init.client`. It renders currently shown prompts in the player's locale, responds to locale and metadata changes, handles deferred property signals without treating its own translation as the source, and disconnects prompt-specific handlers on hide/destruction. Unkeyed static object names use existing `Strings.worldText`; opaque names remain unchanged. Existing world SurfaceGui/BillboardGui label behavior was not altered. Parent should verify actual nearby seller/restore/case/ghetto prompts in EN/ES/FR during Studio QA.

## StudioTestService isolation and startup investigation

`Services/TestSessionScope.Get()` creates one `Run_<GUID>` namespace per server only when `RunService:IsStudio()` and nonempty `StudioTestService:GetTestArgs()` both hold. The server exposes it as `ServerStorage.TestSessionScope`; the Actions harness asserts/reports it. In that mode only negative-ID players use `PlayerProfiles_v3_QA` and `PlayerTransfers_QA_v1` with that shared DataStore scope. Real positive owner IDs and all production servers keep their previous profile/mailbox stores. No existing profile or mailbox is copied, deleted or migrated. A new test run therefore starts fresh instead of reusing persistent `User_-1`, `User_-2`, `Inbox_-1` or `Inbox_-2` from previous failed runs.

Transfer packets carry their test scope. A mismatched old-run packet is rejected before credit or incoming-barrier mutation, and a transfer between simulated and positive-ID players is refused. The offline actual-module suite verifies source save routing, recipient mailbox routing, cross-run replay rejection, unchanged positive-user routing, fresh next-run profiles and both guards on namespace activation. Same-server simulated reconnects share the current scope; a different server/test run intentionally does not reuse it. Production cross-server receipt recovery remains covered by the independent mocked-job boundary tests, with public-server acceptance still pending.

Parent reported both full-sync test clients logged `client ready (ru)` at 22:04:42.917 and 22:04:45.096, with the server started at 22:04:38.154. That evidence rules out a permanently blocked init for that failed setup run. Parent identified a possible Ready-handshake race in the separate PvP harness and owns that correction. No speculative startup-error suppression or additional waits were added to client init. PromptLocalizer itself has no remote waits and its deferred-signal tests pass.
